# /debug — 体系的デバッグ

ランダムな修正を試みる前に、根本原因を体系的に特定する。

## 4フェーズプロセス

### Phase 1: 症状の記録

1. 何が起きているか（実際の動作）を正確に記述する
2. 何が期待されるか（期待される動作）を記述する
3. 再現手順を特定する
4. エラーメッセージ・スタックトレースがあれば全文を確認する

### Phase 2: 仮説の構築

1. 症状から考えられる原因を **3つ以上** リストアップする
2. 各仮説の確からしさを評価する
3. 最も可能性の高い仮説から検証する

### Phase 3: 仮説の検証

1. 仮説を検証するための**最小限のテスト**を設計する
2. テストを実行して仮説を確認または否定する
3. 否定された場合、次の仮説に進む
4. ランダムなprint文やコード変更で探索しない

### Phase 4: 修正と防御

1. 根本原因を特定したら、**最小限の修正**を適用する
2. 修正が問題を解決したことをテストで確認する
3. 同種のバグを防ぐ回帰テストを追加する

## ルール

- 根本原因を特定する前に修正コードを書かない
- 同じアプローチを3回試して進展がなければ、別のアプローチに切り替える
- 関係のないコードを巻き添えにリファクタリングしない

## 引数

`$ARGUMENTS` が指定された場合、そのバグ/エラーに対してデバッグプロセスを適用する。
